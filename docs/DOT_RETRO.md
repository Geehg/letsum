# 도트레트로 — 구현 및 리소스 검토

2026-10-29. 운영 반영 전 구현·로컬 검증 완료.

## 판단

첨부 참고의 핵심은 단색 잉크와 종이색으로 사진의 명암을 재현하는 디더링/망점 인쇄다. AI 모델이나 서버의 이미지 처리 없이 브라우저만으로 서비스할 수 있다. 기존 화방의 로컬 이미지 입력, 별도 Worker 계산, Canvas 출력·PNG 다운로드 구조를 따른다. 문자 매칭/3D 타자기/OpenCV는 이 효과에 필요하지 않아 도트 엔진에서 불러오지 않는다.

참고와 같은 계열의 질감은 구현했지만 피사체 추출, 구도 구성, Photoshop의 특정 필터와 완전히 같은 결과를 보장하는 것은 아니다. 배경도 명암 변환된다. 피사체만 인쇄하려면 배경을 정리한 이미지나 투명 PNG가 가장 적합하다. ‘종이색 없이 투명하게 저장’은 잉크가 없는 픽셀을 투명하게 만드는 기능으로, 피사체 배경 분리와 다르다.

## 구현

- 헤더 `서가 → 화방 → 도트레트로`, 경로 `#/dot-retro`.
- JPG/PNG/WebP 파일 선택·드롭, 자체 제작 금속 자물쇠 예제.
- 레트로 입자(결정적 난수 임계값), 디더링(지그재그 Floyd–Steinberg), 하프톤(명암 면적을 맞춘 원형 망점).
- 점 크기·대비·밝기, 4가지 색 조합 및 직접 잉크/종이색 선택.
- 원본/결과 전환, 실제 크기 스크롤, 투명 PNG, 표시한 결과 그대로 PNG 저장.
- 데스크톱 기본 긴 변 1,600px, 최대 2,400px. 모바일/감지 가능한 저메모리 기기 기본 1,200px, 최대 1,600px. 원본 이상 확대하지 않음.
- 입력 20MiB, 2,400만 화소 제한. 이미지 해상도 검사는 브라우저 디코딩 후이므로 디코더의 순간 메모리까지 제한하는 장치는 아님.
- 180ms 입력 지연, 이전 Worker 즉시 종료, 경로 이탈/새 입력의 오래된 결과 무시, 20초 타임아웃·중단·재시도. 완료 때도 Worker 종료. ‘사진 지우기’는 소스/결과 Canvas를 해제.
- 파일은 업로드·localStorage·계정 저장하지 않음. 페이지 갱신 시 작업 소실. 별도 이미지 API/Worker 배포/DB 변경 없음.

## 서버 비용

| 항목 | 추가 사용량 |
|---|---|
| 사진 변환 CPU/GPU | 서버 사용 없음. 사용자 브라우저의 CPU에서 계산 |
| 사진 저장 공간·DB | 없음 |
| 이미지 업로드/결과 다운로드 트래픽 | 서버 통과 없음. 선택한 파일과 결과를 기기 안에서 처리 |
| 서비스 코드 | 신규 JS/CSS 합계 21,137 bytes, 화면 마크업 5,083 bytes. 총 약 26.2KB, 파일별 gzip 합산 환산 약 10.5KB |
| 방문자 증가 | 정적 파일 요청 증가. CDN/브라우저 캐시에 따라 원본 NAS 요청은 감소. 이미지 수에 비례한 서버 변환 부하는 없음 |

위 크기는 기존 필사독서 페이지·공통 JS·글꼴·서가 데이터의 로딩 비용을 제외한 **이번 기능의 증가분**이다. gzip 수치는 계산값이며 서버가 압축 전송한다는 실측은 아니다. 서버 HTTP/TLS/파일 응답 비용은 있으므로 사이트 운영비 전체가 0이라고 뜻하지 않는다. 신규 유료 인프라나 GPU 서버는 필요 없다.

## 사용자 기기 비용

RGBA 8비트 버퍼 하나는 `가로 × 세로 × 4 bytes`다. 100만 화소 4MB, 400만 화소 16MB, 2,400만 화소 원본 디코딩은 픽셀만 96MB다. 버퍼를 Worker로 **이전**해 전송용 복제를 피한다.

이번 엔진의 명시적 작업 배열은 입력+출력 `8WH` bytes와 격자 명암/알파 `8 × ceil(W/step) × ceil(H/step)` bytes, 작은 2개 오차 행이다. Canvas 소스/원본/결과와 브라우저 디코더, GPU 업로드, PNG 인코더는 별도다.

| 출력 | 엔진 작업 배열(기본 점 크기) | Canvas 3장까지 포함한 계획용 대략값 |
|---|---:|---:|
| 1,000 × 1,000 | 약 10MB | 약 22MB 이상 |
| 2,000 × 2,000 | 약 36MB | 약 84MB 이상 |
| 2,400 × 2,400 | 약 49MB | 약 118MB 이상 |

위 오른쪽은 소스와 출력 크기가 같은 경우의 계산이며 **실제 탭 RSS 측정값이 아니다**. 더 큰 원본의 디코딩 및 PNG 저장이 겹치면 100~250MB 이상을 순간적으로 사용할 수 있다. 메모리 부족/저사양 모바일에는 작은 원본과 1,200px 권장. 처리 중 CPU·배터리·발열을 사용하지만 완료 후 반복 연산은 멈춘다. Worker는 화면 조작과 계산을 분리하며 총 CPU 사용량을 없애는 장치는 아니다. 디코딩/Canvas 복사/PNG 인코딩 비용은 남는다.

## 실측

macOS, Headless Chrome 156, 브라우저가 보고한 논리 코어 10개 환경. 그라데이션 RGBA 입력, 각 조합 4번 중 첫 실행을 제외한 3회 중앙값. 각 실행마다 새 Worker. 다른 기기의 속도 보장치가 아니다.

| 출력 | 레트로 입자 | 디더링 | 하프톤 |
|---|---:|---:|---:|
| 1,000 × 1,000 | 15ms | 16ms | 12ms |
| 2,000 × 2,000 | 34ms | 36ms | 34ms |
| 2,400 × 2,400 | 44ms | 45ms | 50ms |

표는 Worker 내부 변환 시간. Worker 시작+전달/회수까지 포함한 중앙값은 각각 15~20ms, 37~39ms, 47~52ms. 파일 디코딩, 180ms 조작 지연, 화면 출력, PNG 인코딩은 제외. 1,200×1,400 자체 예제의 일반 화면 변환 전체는 해당 실행에서 46~68ms(조작 지연 제외); 처음 페이지를 열 때 다른 초기화가 겹친 실행에서는 약 0.6초도 관찰. 모바일 검사는 390px Chrome 에뮬레이션이며 실물 iPhone/Android 성능·Safari 동작은 아직 미검증.

## 검증

- `node tools/check_typing_dot.cjs`: 순백/순흑/투명, 명암 밀도와 순서, 결정적 결과, 밝기, 색상, 공간 형태, 크기 제한, DOM ID 충돌.
- 실제 Chrome: 세 효과, 원본/결과, 확대, 색 조합, 투명 픽셀, PNG 파일 다운로드, 설정 직후 오래된 결과 저장 차단, 잘못된 PNG, 사용자 첨부 PNG 입력, 사진 삭제, 서가/화방 왕복, 직접 URL 진입.
- 390px 모바일: 화면 가로 넘침 없음, 기본 1,200px/2,400px 선택 제한. JS 예외 없음.
- 변환 시나리오에서 POST/PUT 등 전송 요청 0건. 코드에 사진 네트워크 전송 경로 없음.
- 기존 필사 시작/모델 선택 및 화방 엔진/재생 검사 통과. 전체 `python3 -I tools/validate.py`: 오류 0, 기존 경고 264.

## 원본/생성물

- `tools/typing_app.html`: 화면 원본. `tools/build_pages.js`: 헤더 메뉴.
- 생성 `html/type/index.html`을 직접 수정하지 않는다.
- `html/js/typing-dot.js`: 입력/화면/Worker 생명주기/저장.
- `html/js/typing-dot-core.js`: 순수 픽셀 변환. `typing-dot-worker.js`: Worker 진입점.
- `html/css/typing-dot.css`: 독립 스타일.
- 기존 `typing.js`는 새 경로 제목/서가 상태 처리, `typing-studio.js`는 메뉴 선택 표시만 변경.

## 기술 근거

- [MDN — Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers): UI와 분리된 스레드에서 계산.
- [MDN — Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects): ArrayBuffer 소유권 이전으로 복제 없이 전달.
- [MDN — ImageData.data](https://developer.mozilla.org/en-US/docs/Web/API/ImageData/data): RGBA 픽셀 배열.

OffscreenCanvas도 선택지이지만 현재 구현은 일반 Canvas + Worker의 숫자 배열 처리만 사용하여 별도 그래픽 API 의존을 줄였다. 실제 Safari/Firefox 검증 및 극단적인 파일 디코딩 제한은 후속 점검 항목이다.
